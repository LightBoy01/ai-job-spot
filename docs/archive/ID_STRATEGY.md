# Unified ID Generation Strategy

**Objective:** To establish a clear, consistent, and collision-proof strategy for generating unique document IDs for all content types within the project.

This strategy is critical for ensuring data integrity, preventing content from being overwritten, and making the data more predictable and debuggable.

---

### **ID Structure**

All document IDs will follow a `type-<identifier>` format.

#### **1. Jobs**

*   **Format:** `job-<hash>`
*   **Example:** `job-a1b2c3d4e5f6...`
*   **Implementation:** The ID is a SHA256 hash of the normalized company name, job title, and location.
*   **Responsibility:** This is generated by the `generateJobHashId` function in the `src/data-pipeline/main.ts` orchestrator.

#### **2. Editorials**

*   **Format:** `editorial-<slug>`
*   **Example:** `editorial-the-future-of-ai`
*   **Implementation:** The ID is the slug defined in the frontmatter of the article's Markdown file.
*   **Responsibility:** This is manually set by the content creator when writing an article.

#### **3. Briefings (New Content Type)**

*   **Format:** `briefing-<hash>`
*   **Example:** `briefing-f6e5d4c3b2a1...`
*   **Implementation:** The ID will be a SHA256 hash of the `originalUrl` of the curated article.
*   **Responsibility:** This will be generated by the new "Briefings" data pipeline when it creates the content file. Using a hash of the URL guarantees uniqueness and idempotency (running the pipeline again on the same article will produce the same ID).

---

### **Rationale**

*   **Collision-Proof:** By prefixing each ID with its type, we guarantee that a job, an editorial, and a briefing can never have the same ID, even if their titles or other attributes are identical.
*   **Clarity:** The ID format makes the content type immediately obvious when looking at the raw data in Firestore or in the filesystem.
*   **Consistency:** This provides a single, documented convention for all current and future content types.
