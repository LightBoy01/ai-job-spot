# Data Pipeline Flow

This document outlines the end-to-end flow of data for both the Jobs and Briefings pipelines, fulfilling Task 1.3.

## Entry Points

The pipeline is initiated via npm scripts defined in `package.json`:

- **Jobs Pipeline:** `npm run pipeline:jobs`
- **Briefings Pipeline:** `npm run pipeline:briefings`
- **Seeding to Firestore:** `npm run seed`

These scripts execute `src/data-pipeline/main.ts` (for the pipelines) and `seedFirestore.ts` (for the seeder), which are the primary orchestrators.

## Jobs Pipeline: Step-by-Step Flow

1.  **Initiation:** `npm run pipeline:jobs` calls `main.ts`, which in turn calls `orchestrateJobs()`.

2.  **Configuration Loading (`getJobSources`):
    *   The system first checks for a local cache (`.cache/data-pipeline/sources.json`) to find job source configurations.
    *   If the cache is missing or stale (older than 24 hours), it fetches the configurations from the `job-sources` collection in Firestore.
    *   Alternatively, if run with `--use-local-config`, it loads from `pipeline.config.local.ts`.
    *   The raw configurations are validated using a Zod schema in `pipeline.config.jobs.ts`.

3.  **Adapter Creation:** For each valid source configuration, `source-adapter-factory.ts` creates the appropriate adapter (e.g., `HiringCafe`, `RSS`, `Playwright`).

4.  **Data Fetching:** The `runSource()` function in `main.ts` calls the `fetchJobs()` method on each adapter. The adapter retrieves raw job data from the external source.

5.  **ID Generation & Deduplication:**
    *   For each raw job item, a unique, content-based hash ID is generated by `utils/id-generation.ts`.
    *   The pipeline compares the set of remote IDs with the IDs of existing local Markdown files for that source to identify new, existing, and stale jobs.

6.  **Archiving:** Stale local files (jobs that no longer exist in the remote source) are moved to the `scripts/archive/` directory.

7.  **Transformation & Normalization:**
    *   Each new or updated raw job item is passed to the adapter's `transform()` method.
    *   This method standardizes the data into the `StandardJob` format defined in `types.ts`.
    *   Company names, job titles, and locations are normalized using functions from `src/lib/normalization.js`.

8.  **Error Handling (DLQ):** If the transformation fails for any item, `utils/dlq.ts` writes the raw item and the error details to a JSON file in the `data/dead-letter-queue/` directory for later reprocessing.

9.  **File Writing (`writer.ts`):
    *   The final, standardized `StandardJob` object is passed to `writeJobFile()`.
    *   The content is sanitized using `DOMPurify`.
    *   The data is split into YAML frontmatter and a Markdown body.
    *   The final content is written to a new `.md` file in `src/job-descriptions/`.

## Briefings Pipeline Flow

The Briefings pipeline follows the exact same pattern as the Jobs pipeline, with a few key differences:

- **Entry Point:** `npm run pipeline:briefings`.
- **Orchestrator:** `orchestrateBriefings()` in `main.ts`.
- **Configuration:** Fetches from the `sources` collection in Firestore where `type == 'Article'`. The schema is defined in `pipeline.config.briefings.ts`.
- **Adapter:** Currently uses the `RSS` adapter (`adapters/rss-adapter.ts`).
- **Transformation:** The `transform()` method in the RSS adapter also uses `parsers/article-parser.ts` to fetch the full article content from the source URL and convert it to Markdown.
- **Output:** Final `.md` files are written to `src/content/briefings/`.

## Seeder Flow (`seedFirestore.ts`)

1.  **Initiation:** `npm run seed` executes the compiled `seedFirestore.ts` script.
2.  **Processing:** The `processDirectory` function reads all `.md` files from `src/job-descriptions/` and `src/articles/`.
3.  **Validation & Sync:** It validates the frontmatter against Zod schemas, compares the local file IDs/slugs against those in Firestore, and calculates the difference (new, updated, and deleted items).
4.  **Database Operations:** It uses batch operations to `set` (upsert) new/updated content and `delete` orphaned content in Firestore.
5.  **Cache Revalidation:** It calls the `/api/revalidate` Next.js endpoint to purge the cache for all modified pages.
6.  **Indexing:** It notifies the Google Indexing API of all changed URLs.
