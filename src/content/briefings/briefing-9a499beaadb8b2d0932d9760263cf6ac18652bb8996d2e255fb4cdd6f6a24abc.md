<h2>
  
  
  ℹ️ Description and Rationale
</h2>

<p>For years, Java developers have treated API versioning like the “awkward cousin” of REST design. We all knew we needed it, but Spring never gave us a standardized way to do it. Developers had to implement it manually using one of the common strategies (often inconsistently across teams or projects). We wrote custom interceptors, hacked URL paths manually, or cluttered our code with @RequestMapping(“/v1/…”), @RequestMapping(“/v2/…”), etc. That changes now.</p>

<p>With the arrival of <strong>Spring Boot 4.0</strong>, API versioning is a first-class citizen. It is native, declarative, and surprisingly powerful.</p>

<p>This guide explores handling this using a simple Hospitality Management App — my current domain — focusing on versioning with the clean, standardized style of Spring Boot 4.</p>




<h2>
  
  
  🛑 The Problem: Why “DTOs” Are Not Enough
</h2>

<p>A common question I hear is:<br>
<em>“Why do I need versioning? Can’t I just update my DTOs?”</em></p>
<h3>
  
  
  🏨 Imagine you run a hotel:
</h3>

<ul>
<li>The scenario: You have legacy Self-Check-In Kiosks in the lobby. They expect a room ID as an Integer.</li>
<li>The innovation: You launch a new Mobile App. It uses secure UUIDs for room IDs and offers “Virtual Keys.”</li>
<li>The Crash: If you update your DTOs to change id from Integer to UUID, every kiosk in your lobby crashes instantly.</li>
</ul>

<p>It lets the old Kiosks (V1) and the new Mobile App (V2) communicate with the same backend simultaneously without conflict.</p>


<h2>
  
  
  🕰️ Before v/s After: The Evolution
</h2>

<p><a href="https://media2.dev.to/dynamic/image/width=800%2Cheight=%2Cfit=scale-down%2Cgravity=auto%2Cformat=auto/https%3A%2F%2Fdev-to-uploads.s3.amazonaws.com%2Fuploads%2Farticles%2Fv78bsjtd6mdfxsjrb1tm.png" class="article-body-image-wrapper"><img src="https://media2.dev.to/dynamic/image/width=800%2Cheight=%2Cfit=scale-down%2Cgravity=auto%2Cformat=auto/https%3A%2F%2Fdev-to-uploads.s3.amazonaws.com%2Fuploads%2Farticles%2Fv78bsjtd6mdfxsjrb1tm.png" alt="API Versioning: Spring Boot 3 v/s Spring Boot 4" width="800" height="315"></a></p>
<h3>
  
  
  🏁 Key Highlights
</h3>

<ul>
<li>New version attribute on all mapping annotations (e.g.: On @RequestMapping, @GetMapping, etc.)</li>
<li>Same path, different versions in one controller — clean and co-located</li>
<li>Supports semantic versioning (major.minor.patch) with ranges and baselines:</li>
</ul>

<blockquote>
<p>version = "1.0" → exact<br>
version = "2+" → 2.0 and all compatible newer versions until overridden<br>
Automatic selection of the highest compatible version</p>
</blockquote>

<ul>
<li>Customising the version parsing with ApiVersionParser interface</li>
<li>Built-in deprecation handling: Auto-add Deprecation, Sunset, Link headers for old versions through @Configuration</li>
<li>Works seamlessly with clients (RestClient, WebClient) and tests (MockMvc, WebTestClient, etc)</li>
<li>400: Bad Request if no version is provided (unless configured otherwise) with setVersionRequired(boolean)</li>
<li>And, many more we’re going to learn below…</li>
</ul>


<h2>
  
  
  &nbsp;ℹ️ API Versioning: Four strategies (The Introduction)
</h2>

<p>Spring Boot 4 supports all four major versioning strategies out of the box. In our Hospitality App example, we will configure all of them to demonstrate flexibility.</p>

<blockquote>
<p>Please Note: Path Segment Versioning cannot combine with other strategies. Once enabled, it takes precedence and overrides other versioning methods. For clarity and consistency, select one or two strategies (max) and apply them consistently across your application.</p>
</blockquote>
<h3>
  
  
  &nbsp;1️⃣ Path Segment Versioning (The Standard)
</h3>

<ul>
<li>Format: /api/v1/rooms</li>
<li>Best For: Public APIs, OTAs (Expedia/Booking.com, Distribution, etc). Easy to cache via CDNs.</li>
</ul>
<h3>
  
  
  2️⃣ Header Versioning (The Cleanest)
</h3>

<ul>
<li>Format: Header X-API-Version: 2.0 with URL /api/rooms</li>
<li>Best For: Internal Micro-services. Keeps URLs clean and “resource-focused.”</li>
</ul>
<h3>
  
  
  &nbsp;3️⃣ Query Parameter Versioning (The Quickest)
</h3>

<ul>
<li>Format: /api/rooms?version=1.0</li>
<li>Best For: Ad-hoc scripts, quick debugging, or legacy browser clients.</li>
</ul>
<h3>
  
  
  4️⃣ Media Type Versioning aka Content Negotiation (The Purist)
</h3>

<ul>
<li>Format: Set Header (any one to individual APIs) as:</li>
</ul>

<blockquote>
<p>Accept: application/vnd.hotel.v2+json<br>
Accept: application/vnd.api+json; version=2.0<br>
Accept: application/json; version=2.0</p>
</blockquote>

<ul>
<li>Best For: Strict REST paradigms where the representation changes, not just the data.</li>
</ul>

<h2>
  
  
  🙌 Bonus: Functional Endpoints
